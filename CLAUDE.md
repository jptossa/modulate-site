# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Modulate helps people find alternative careers from job-market data. Guests chat with an agent for recommendations; account holders also get tools that read their profile and log the career routes they choose. Stack: Next.js 16 (App Router, plain CSS, no Tailwind) + Supabase (Postgres, Auth, RLS) + Claude via the Vercel AI SDK.

`AGENTS.md` is generated by Next and is right: this Next.js has breaking changes, so read the relevant guide in `node_modules/next/dist/docs/` before writing Next code.

## Commands

```bash
npm run dev          # dev server on :3000 (preview config in .claude/launch.json, name "modulate-dev")
npm run build        # production build; also regenerates route types
npm run lint
npm run typecheck    # tsc --noEmit
npm run tokens       # regenerate styles/tokens.css from design-system/tokens.json

npm run ingest:onet  # O*NET occupations, skills, ratings   (add -- --dry-run to only parse)
npm run ingest:bls   # BLS projections -> occupation_market
npm run ingest:oews  # OEWS annual employment -> occupation_series
npm run db           # scripts/db.mjs inspect | migrate (see Database)
```

- There is no test runner yet.
- `PageProps<"/route">` and `LayoutProps<"/route">` are global types generated by Next. After adding a route, `npm run typecheck` fails with "does not satisfy the constraint" until `npm run build` (or `next dev`) regenerates them.
- Never read `.env` or print its values; it holds the Supabase and Anthropic keys. Scripts load it with `node --env-file=.env`. `.env.example` lists the variable names.

## Next.js 16 specifics

- `cacheComponents` and `partialPrefetching` are on (`next.config.ts`). Anything that reads `cookies()` or `searchParams` must sit behind a `<Suspense>` boundary or the build fails; never await the session at the top of a layout. See `app/auth/*/page.tsx` for the pattern and `node_modules/next/dist/docs/01-app/02-guides/authentication-with-cache-components.md`.
- Middleware is called Proxy: the root `proxy.ts` calls `updateSession` in `lib/supabase/proxy.ts`, which refreshes the Supabase session cookies on every request and redirects guests away from `PROTECTED` paths (`/routes`, `/profile`). It is only an optimistic check; pages and server actions must call `requireUser()` / `getCurrentUser()` from `lib/auth.ts`, which verify with `supabase.auth.getUser()`. Without Supabase env vars the proxy passes through, so public pages still render.

## Design system

The source of truth is an external design-system artifact; a snapshot is in `design-system/` (`tokens.json`, `README.md`, `index.d.ts`). Read `design-system/README.md` before building UI: it defines the content rules this app must follow (never invent statistics, mark missing facts as `[PLACEHOLDER]` and example charts as "Illustrative", no emoji, sentence case, verb-first buttons, route/stop/"you are here"/destination vocabulary, Rising/Steady/Cooling and Very high/High/Good/Moderate level words, one primary button per view).

- `styles/tokens.css` is generated; edit `design-system/tokens.json` and run `npm run tokens`. It defines `--<token-name>` variables plus `.type-<style>` classes. `styles/bundle.css` is the design system's component CSS (its Google Fonts `@import` removed).
- Fonts load through `next/font` in `app/layout.tsx`; `app/globals.css` points `--font-sans` / `--font-serif` at them.
- `components/ds/` is a TSX port of the system's vanilla `window.Modulate` bundle and reuses its `md-*` class names. Import from `@/components/ds`. Server/client split matters: `shared.tsx` has no `"use client"` (helpers are called from server components); the reduced-motion hook lives in `motion.ts`; `RouteMap`, `Ticker`, `controls.tsx` are client components.
- `/styleguide` renders every component on example data.

## Supabase and data

Clients in `lib/supabase/`: `server.ts` `createClient()` is the cookie-bound client that runs as the user (RLS applies); `createServiceClient()` bypasses RLS and is server-only; `client.ts` is for the browser. `env.ts` reduces `NEXT_PUBLIC_SUPABASE_URL` to its origin because the dashboard's API URL sometimes carries a `/rest/v1/` suffix.

Database (`supabase/migrations/`, applied in filename order):
- Reference data (`occupations`, `skills`, `occupation_skills`, `occupation_market`, `occupation_series`) is public read; only the service role writes it. User data (`profiles`, `user_skills`, `saved_routes`) is owner-only via RLS; a trigger creates the profile on sign-up. `rate_limits` is touched only through the service-role-only `bump_rate_limit()`.
- **This Supabase project does not auto-grant API access.** Every new table, view and function needs explicit `GRANT`s to `anon` / `authenticated` / `service_role` (see `..._grants.sql`), or requests fail with 42501 before RLS runs.
- Migrations are applied by pasting them into the Supabase SQL Editor. The hosted DB host is IPv6-only, so `scripts/db.mjs` cannot connect from the dev machine without a pooler host in `DB_HOST` / `DB_USER`.
- Role similarity is `adjacent_occupations(origin_soc, lim)`: cosine of **mean-centred** importance x level vectors (`skills.mean_weight`, written by the O*NET ingest), clamped to 0..1. Raw cosine scored nearly every pair 0.74-0.98 and was unusable. The overlap level thresholds (0.85 / 0.75 / 0.65) live in `components/ds/shared.tsx` `overlapLevel()`. The closest matches to a role are mostly its own occupation family (teachers return teachers), so recommendation code must drop the origin's own minor group (first four characters, e.g. `25-2`). Even then the next-closest roles are often the same major group (teachers return postsecondary teachers, `25-1`), so `adjacent_roles` lists other major groups first and only backfills from the same major group. `skill_gap(origin, dest)` returns the destination's top skills with a `has` flag.

Ingest scripts (`scripts/ingest/`) read raw files from `data/` (git-ignored, see `data/README.md` for sources and exact download steps) and write through the service role over REST:
- O*NET 31.0 (CC BY 4.0, attribution required on the site): the text database has no `Skills.txt`; skills come from `Essential Skills` and `Transferable Skills`, knowledge from `Knowledge`. Only the 761 occupations O*NET rated are loaded, keyed by 6-digit SOC (the `.00` base code).
- BLS Employment Projections (2025-35): bls.gov blocks scripted downloads, so the files are downloaded manually in a browser. 24 occupations are reported by BLS only as part of a group; they get the group's growth, pay and trend but null employment and openings, and `source` says so. `bls.mjs` imports `lib/market/trend.ts` directly through Node's type stripping, so keep that file to erasable TypeScript syntax. Trend cut points: Rising >= +6%, Cooling <= -2%.
- OEWS annual history (2019-2025) is the only history available: the BLS API holds just the latest OEWS year. BLS discourages OEWS for time series (method changes in 2021 and 2022), so label charts "annual estimates"; series with a 40%+ one-year swing are left out. BLS publishes no monthly per-occupation openings.

## Auth

`app/auth/actions.ts` (server actions: `signIn`, `signUp`, `signOut`) with `components/auth/AuthForm.tsx`. Email confirmation is off (`supabase/config.toml`, and in the hosted dashboard). `safeNextPath()` in `lib/auth.ts` guards the `?next=` redirect against open redirects.

## Chat agent

`app/api/chat/route.ts` runs a `ToolLoopAgent` (AI SDK v7; docs are in `node_modules/ai/docs/`, they differ from older tutorials) with `createAgentUIStreamResponse`. Two model tiers: `CHAT_MODEL` (default `claude-haiku-5-5`) answers, and can call the `escalate` tool to hand the rest of its reply to `CHAT_ESCALATION_MODEL` (default `claude-sonnet-5-5`) via `prepareStep` (`lib/chat/escalation.ts`, state is per request). Escalations are capped per person per day (`SONNET_DAILY_LIMIT`, default 10; separate `sonnet:` bucket in `rate_limits`); over the cap the tool returns `escalated: false` and Haiku carries on. If both env vars name the same model the tool is not offered. Conversations are session-only (nothing persisted except saved routes and profile).
- Tools live in `lib/chat/`: `market-tools.ts` (everyone: `search_occupations`, `adjacent_roles`, `market_trend`, `skill_gap`) and `account-tools.ts` (signed-in only: profile and saved routes, on the RLS-bound client). `buildTools(db, user)` picks the set from the verified session; no tool takes a user id from the model. Tool output shapes are in `lib/chat/types.ts`, shared with the client cards. Tools return `{ error }` instead of throwing for expected problems.
- Rate limit (`lib/chat/rate-limit.ts`): `bump_rate_limit` through the service client, guests by sha256(`RATE_LIMIT_SALT` + IP) at `GUEST_DAILY_LIMIT` (default 20), users by id at `USER_DAILY_LIMIT` (default 200). Fails closed. Locally the guest IP is `::1`.
- `/chat` (`app/chat/page.tsx`) is public. The session read must call `await connection()` before `getCurrentUser()`: with `partialPrefetching` the runtime prefetch otherwise trips "unstable value `Date.now()`" inside Supabase auth.
- UI: `components/chat/ChatThread.tsx` (`useChat`) renders tool parts (`tool-<name>`) through `ToolResult.tsx` as design-system cards. The system prompt (`lib/chat/system-prompt.ts`) asks for plain text because the thread does not render Markdown.
- Floating widget: `components/chat/ChatWidget.tsx`, mounted in the root layout behind `<Suspense>` (it uses `usePathname`; never read the session there). It is a modal `<dialog>` (native focus trap, Escape, focus return) holding `<ChatThread variant="widget" />`, which stays mounted so the conversation survives closing and client-side navigation (a reload clears it). It hides itself on `/chat` and `/auth/*`. In the panel CSS hides the route map (`.chat-console`), because its labels are unreadable at ~440px; the route options carry the same facts. The API returns `code: "guest_limit" | "user_limit"` on a 429 so the client never matches message text. Chat CSS lives in `components/chat/` and loads site-wide.
- `search_occupations` calls the `search_occupations(q, lim)` RPC (pg_trgm `word_similarity`, migration `..._search_occupations.sql`). It is fuzzy but not semantic: O*NET's formal titles ("Secondary School", not "high school") still need the model to retry with other words. If the migration has not been applied the tool falls back to AND-ed `ilike`; remove that fallback once it is applied everywhere.

## Local market data

Reference tables `areas` (national, state, metro, nonmetro; BLS `AREA` codes as text) and `occupation_area_market` (latest OEWS employment, median pay, location quotient per area and occupation; suppressed cells are null) come from migration `20261029000000_areas.sql`, which also adds `profiles.area_code` and the `search_areas(q, lim)` RPC; `20261029000100_area_pay_top_coded.sql` adds `median_pay_top_coded` (BLS prints "#" for a median at or above $239,200; it loads as that cap with the flag, and the UI says "$239,200 or more"). `npm run ingest:areas` (`scripts/ingest/oews-areas.mjs`) loads May 2025 from the national, state and metro workbooks under `data/bls/oews-2025/`; the dry run is checked against the real files (585 areas: U.S., 54 states and territories, 393 metros, 137 nonmetro; about 201,000 rows), and add `-- --dry-run` to preview a reload. Apply the migration and run the ingest before merging: the profile page selects `area_code`.

- Place search is `search_areas` (migrations `20261029000200_area_search.sql`, tuned in `…000300_area_search_tune.sql`): an exact nickname in `areas.aliases` ("bay area", "dfw", "nyc") returns only those places; otherwise fuzzy matching with filler words ("area", "metro", "region") stripped from both sides and nonmetro areas ranked down unless the query says rural. Add nicknames there; BLS names metros after principal cities only.
- `getPreferredArea(db, user)` (`lib/area.ts`) is the profile's area for signed-in users and the `modulate_area` cookie for guests. It reads cookies: call it behind `<Suspense>` after `await connection()`. `setArea` / `searchAreaOptions` (`lib/area-actions.ts`) write it; `components/area/AreaPicker.tsx` is the search-and-pick UI (profile page, collapsed `<details>` on `/routes/visualize`).
- Local figures are only pay, jobs and concentration. Trend, projected change and openings stay national (BLS publishes no local projections); never label a local number with those words, and never fall back to a national number under a local label. A missing cell shows "No local estimate".
- Local pay is comparable with national pay: `occupation_market.median_pay` is the May 2025 OEWS national median (identical to the national row in `occupation_area_market` for all 732 roles both cover). `comparePay` / `describePayComparison` in `lib/market/compare.ts` turn the two into "12% above the U.S. median" (within 3% reads "About the U.S. median"; a capped local median reads "At least"); chat returns it as `local.payVsNational`.
- Visualizer: `getVisualizerData(db, userId, area)` attaches `RouteVisual.local` from a `"use cache"` reader keyed by area code and destinations; `RouteVisualizer` has a National or local `SegmentedControl` and `ComparisonBars` takes `area`.
- Chat: `search_areas` for everyone; `market_trend` and `adjacent_roles` take optional `area_code` / `national_only` and default to the saved area passed to `buildTools(db, user, area)`; signed-in users also get `set_area`. The route handler catches a failed area read so chat still works before the migration is applied.
- Setting a place is meant to be quick for guests: `AreaPicker` searches as you type (250 ms debounce, newest search wins) and, until a place is set, shows `suggestions` as chips. `getPopularAreas()` (`lib/area.ts`, `"use cache"`) resolves big-metro nicknames through `search_areas` instead of hard-coding BLS codes. `ChatPlace` and `components/landing/LandingPlace.tsx` (a collapsed picker in the hero, passed to `LandingExplorer` as the `place` slot like `signUp`) both use it; the landing charts stay national. In chat, `search_areas` results draw a `PlacesCard` of buttons that call `setArea` (guests have no `set_area` tool, so the guest prompt tells the model to ask them to press one).
- Not built: local employment history (`occupation_area_series`), state projections.

## Military crosswalk

Military codes to civilian roles, from the O*NET Military Crosswalk (separate download, see `data/README.md`; CC BY 4.0, attribution is in `LandingBands.tsx` and the chat footer). Migration `20261030000000_military_crosswalk.sql` adds `military_occupations` (branch, category enlisted/officer/warrant, code, `code_key`, title, `active`, `other_links`), `military_roles` (code to SOC, `position` is O*NET's listing order, not a strength) and `profiles.military_id`; `npm run ingest:military` (`scripts/ingest/military.mjs`, reads the CSV, add `-- --dry-run`) loads them. Apply the migration before the ingest, and before the profile page or chat tools are used: they read `military_id` separately and degrade (no military block, tool returns an error) if it is missing.

- A row is (branch, category, code): the same code means different things per category. The crosswalk's service letters fold into six branches (Space Force rows duplicate Air Force codes in the source). Where a service reuses a code the active record wins; retired codes stay, flagged `active: false`, because veterans hold old ones. Roles are limited to the SOCs in `occupations`, so combat and other military-only jobs (Infantry, `55-` codes) load with no roles and their O*NET titles in `other_links`; the UI and prompt say "no civilian match" rather than inventing one. "All Other" catch-all roles are not loaded either.
- `search_military(q, lim, branch_filter)` RPC (latest definition in `20261030000100_military_search_tokens.sql`; a code written in capitals inside a sentence, "I was a Navy HM", counts as a code): an exact code hit (normalised: case, spaces, hyphens) returns only exact hits (so "IT" is the Navy rating, not every title containing "it"), otherwise fuzzy title match; active codes first. An X in the fourth place of an Air Force or Space Force code ("3D0X2") matches any skill level ("3D032"). `lib/military/queries.ts` `searchMilitary` collapses results that share roles (skill levels) and attaches roles; `militaryById` reads one code. `lib/military/labels.ts` is client-safe.
- Chat: `search_military` for everyone (`market-tools.ts`, `MilitaryCard` in `ToolResult.tsx`, prompt fragment `MILITARY`); signed-in users also get `set_military_background(military_id)` and `get_profile` returns `military`. The tool's role `soc` values feed `adjacent_roles` and `skill_gap`.
- Profile: `MilitaryForm` (`components/account/ProfileForms.tsx`) with `searchMilitaryCodes` / `setMilitaryBackground` in `profile/actions.ts`; each matched role has "Use ... as current role". Landing: `LandingMilitary` (collapsed picker in the hero) calls `lib/landing/military-actions.ts` (guest-open, public client), which builds an origin with the exported `buildOrigin`; `LandingExplorer` appends it to its chips in client state (labelled "Army 68W"), so the cached bundle is untouched.
- Not built: the COOL and ASVAB supplemental files (credential and skill hints per code).

## Design studio

`design-studio/` is a standalone tool for trying design-system changes (colour and type) without touching the app: one self-contained `design-studio.html` (plain HTML/CSS/JS, no framework, no connection to the app or its database) plus the prototypes it was ported from, `color-playground.html`, `type-playground.html`, `layout-playground.html`, `token-cascade.html` (with its `tokens.css`) and `share-playground.html`, kept as reference. Start it with `npm run studio` (or the `design-studio` preview in `.claude/launch.json`); both run `design-studio/serve.mjs` on :8765. Serve it rather than opening the file in a preview pane: a pane shows files it did not serve as static snapshots with scripts off, and the page says so in a red note when that happens.

- The preview components are a static copy of the app's own markup (from the rendered `/styleguide`) and CSS (`styles/bundle.css`, `motion.css`, `axes.css`), with the fixed font sizes, weights, spacing and line heights of the `md-*` components replaced by studio CSS variables so every control shows up. Regenerate the copy by hand if the components change; it does not follow the app.
- Defaults equal the app's shipped values (`design-system/tokens.json`): base 16, Major Third 1.25, Instrument Sans and Instrument Serif. The font pickers also offer 22 close Google Fonts alternatives for comparison (`FONT_DATA` in the page: weights and italics checked against Google Fonts' metadata; add a family there with its shipped weights). Sizes scale relative to the shipped ones by ratio step (display and call-to-action 4, heading 3, titles and stats 2, lead and card titles 1, the rest 0). Weight roles are dropdowns of the weights the font ships. The preview stays light: the app has no dark mode.
- Layout: the controls are five tabs (Typography, Color, Layout, Tokens, Share; the choice is remembered in `localStorage`). A pill above the preview switches its view: Regular (fills the pane), Desktop (1280px by default, resizable in the Layout tab), Mobile (a 390 x 844 phone screen that scrolls inside, shrunk with `zoom` if the pane is shorter) and Print (Letter paper, 0.5in margins); a frame wider than the pane is shrunk with `zoom`. `.preview` is a named container (`preview`), and the app's responsive rules inside it are `@container preview` queries and `cqw` units instead of `@media` and `vw`, so the frame, not the studio window, decides the layout. Keep that when porting CSS from the app. The fluid-type readout uses the frame width; the copied clamp still says `vw`. Print is a paper-width simulation plus an `@media print` block, not a check of the browser's print engine.
- Page views: Regular keeps the component specimen (`.spec-components`, or the Layout sections). Desktop and Mobile show `.spec-site`, a home page modelled on the app's landing page (header, ticker, hero, console, trends, detail cards, data band, the one coral call to action, footer; the page CSS is copied from `site.css` and `landing.css` with `.container` as `.ps-container`). Print shows `.spec-print`: a two-sheet Letter route report (816 x 1056 px sheets, the dark console replaced by a light route line because printers drop dark backgrounds; sheets grow past Letter height if type or spacing grows). The components in these pages are not retyped: `data-slot="source|selector"` placeholders are filled at load by cloning from the specimen sections marked `data-src`, with the chart marker ids renamed per page (so a change to a specimen component shows up everywhere). All three views (and Regular) respond to the Layout tab. The Print sheets keep their 0.5 in margins; columns, gutter and base unit still apply. Print forces Light (paper is light) and restores Dark afterwards. Copy follows the design-system README: example data, `[PLACEHOLDER]` for missing facts, chart marked Illustrative.
- Layout tab: three groups that act on the real components in every view (there are no sample cards). **Base unit** (4 / 8 / 2-12) sets `--sp` = base / 8 and `--base-unit`; the component CSS copied from the app has every padding, gap and margin written as `calc(Npx * var(--sp))` (touch-target min-heights and fonts are not scaled), so at 8 the app is as shipped. **Page grid**: columns (4-16), gutter and outer margin (As shipped, or space-N = N x base unit), maximum content width (`--content-max`) and a grid overlay (the toggle is the first control in the group, and columns and gutter are disabled until it is on, so they are never edited blind; their values keep applying while it is off). The card rows (`.sg-grid`, `.sg-split`, `.ps-sources`, `.ps-pair`) are CSS grids of `--pg-cols` columns whose children carry `data-span` (wide,medium,narrow: a column count, h = half, r = the rest, f = full); JS (`applyLayout()`) resolves it into `--span` per size. **Responsive**: the `.preview` width picks narrow / medium / wide (defaults below 480 / below 720) and the columns drop to a third / two thirds of the set number (12 becomes 4 / 8); modes are Fluid (always wide), Adaptive (page snaps to a fixed width per size) and Combination (the app's behaviour). Desktop view width is a slider (320-1440). A ruler shows where the current preview sits, and the values are exported from the Tokens tab. All of it is set as custom properties and `data-tier` / `data-rmode` on `.preview`, so every rule falls back to the shipped value without them.
- Tokens tab (from the token cascade): every token in one table (a filter box, per-row sample, text input, reset arrow, edited highlight, **Copy all tokens as CSS**, **Reset tokens**), edited against the real components in every view. The export is every token, not only edited ones (`tokAllCss()`: light and shared values in `:root`, dark colours and shadows in `[data-theme="dark"]`, the Layout tab's page grid and responsive settings last from `layCss()`; edited and proposed tokens are marked in a comment), previewed live in the **Tokens (CSS)** group at the bottom of the tab. **Copy edited only** (`tokAllCss(true)`, same code path) exports just the edited tokens, plus the grid and responsive block when those differ from the shipped ones. One store per token, never two: **colours** use the Color tab's `CUR` / `EDITED` / `setToken()` (a typed hex goes through the same path as the colour picker, so editing `blue` in Light still moves the base colour); **type tokens** (weights, line heights, letter spacings) and `content-max` are linked rows that set the Typography or Layout control and fire its event; **spacing, radius, shadow and border widths** use the override store `TOV` (`shared`, `light`, `dark`; shadows are themed, with the dark values in `TOK_DARK` applied by `applyTok()`). A space token that is not edited shows the shipped value times base / 8; typing a value replaces the token's `calc(Npx * var(--sp))`, so an explicit edit beats the base unit. "Edited" is a diff against the shipped value in the current mode, so colours moved by the base colour or harmony also count and are exported. Derived rows are read-only: font families, the font-size scale (base x ratio^n from the Typography tab) and the base-unit scale (N x base unit, from the Layout tab). The registry `TOK` is written out from `design-system/tokens.json` by hand, like `TOKENS`. **Proposed** tokens come from the cascade's `tokens.css` and are not in the app: the status colours `success`, `warning`, `error`, `info` (also listed in the Color tab, unused by any component), `border-width-default/-emphasis/-focus` (wired into the copied CSS: the focus ring, the route option's 2px border and the 1px hairlines; borders written as 1.5px are not), and the type tokens above. `shadow-card` is in the app but no component uses it by default, so editing it changes nothing visible. The cascade's generic sample card was not ported.
- Share tab (from the share playground): **saved themes** and a **view-only link**. A theme is everything the other tabs change (type controls, colours in both modes plus base colour and harmony, the Layout settings, the token overrides), stored as a difference from the shipped studio (`shSnapshot()`), so links stay short. `shApply()` puts the studio into exactly that state (every control not in the theme goes back to its shipped value, by setting the control and firing the event the studio already listens for), so it reuses the other tabs' own handlers and nothing is duplicated; the control list is `SH_CTL`, and a new control that should be saved has to be added there (or to the colour, layout or token stores it already covers). Saved themes live in `localStorage` (`design-studio.themes.v1`, this browser only, never uploaded) and exclude the view and mode; the **link** is `?s=` plus base64 JSON in the address and includes the view and Light / Dark. Anything read back goes through `shClean()`: only known controls and tokens, values inside each control's range or option list, hex colours only, token values must pass `CSS.supports`, fonts must be in `FONTS`; everything else falls back to the shipped value (checked with a hostile link). Opening a link with `?s=` is read-only: the controls panel is hidden and a bar says so, the preview shows the shared values, the view and mode pills still work, and **Edit a copy** drops the `?s=` and opens the controls with those values. The link opens the studio at its own address, so while the studio runs on 127.0.0.1 it only works on this computer; the tab says so. The playground's `prompt()` and `confirm()` are replaced by an inline name field and a press-again-to-replace button. **Quick edit** (the playground's five-control editor) is the top group: primary colour (`blue`), surface (`surface-raised`), corner radius (`radius-md`), spacing (`space-md`) and base text size. It is a second view of settings that live elsewhere, never a second copy: colours go through `setColour()`, radius and spacing through the Tokens override store (`qkPx()`), text size through the Typography base slider, so the other tabs, saved themes and links already include them; `refreshQuick()` keeps the controls in step. Colours edit the mode shown by the Light / Dark pill. Moving the primary colour re-derives the whole blue and coral family (as in the Color tab), and its reset (`QK_FAMILY`) puts that family back exactly, leaving other colour edits alone.
- Dark mode: a Light / Dark pill above the preview switches the whole preview, the 44 colour token editors and the contrast checker between two token sets (`DEF.light` / `DEF.dark`, `DARK` in the page holds the dark values). The app ships light only, so the dark palette is a proposal: near-black navy surfaces, light text, brand colours lifted. Base colour and harmony derive both modes (`derive()`; the dark blue fill is the lightness nearest the base that holds a white label and the dark page). Editing `blue` in Light moves the base; in Dark it edits only the dark token. The app pairs `ink` with `on-inverse` as fill and label (selected segmented option, inverse button), and uses `ink` on coral, which collide in dark; the studio patches those in `.stage[data-theme="dark"]` CSS, and a real dark mode would need extra tokens for them. The controls panel keeps following the OS colour scheme, independent of the pill.
- Studio headings ("Type styles" and so on) use `.studio-h`, fixed type that no control changes. Anything that would ship in the app uses the token-driven classes.

## Status and what is planned

Built: design system port, `/styleguide`, Supabase schema and auth, the data pipeline above (loaded in the hosted project), the chat agent (below), the account pages, and the route visualizer.

Every page except `/auth/*` sits in the `app/(site)/` route group, whose layout renders `components/site/SiteHeader.tsx`: a static shell (logo) plus `SiteNav`, which shows Sign in / Create an account to guests and Chat / Routes / Profile / Sign out to signed-in users. The session is read only inside the header's `<Suspense>` (after `await connection()`), so the layout stays static. `/auth/*` keeps its own minimal layout.

Account pages live in `app/(site)/(account)/` (its layout is only a container; it never reads the session): `/routes` is the saved-route tracker (`RouteCard` with a `SegmentedControl` status, notes, remove) and `/profile` edits display name, current role and skills. Their server actions sit beside each page and call `requireUser()`; shared route select/mapping is in `lib/routes.ts` (also used by the chat account tools). Like `/chat`, the pages `await connection()` before reading the session. Components are in `components/account/`.

Route visualizer (`/routes/visualize`, `app/(site)/(account)/routes/visualize/`, components in `components/visualize/`, styles in `visualize.css`): the user's own saved routes drawn with the design system, up to three compared at a time (the DS has three route identities). `RoutesSubnav` switches between the list and this page; the editing pages wrap their content in `.account-narrow` (760px) so the visualizer can use the full container. `lib/visualize/data.ts` `getVisualizerData()` reads `saved_routes` on the RLS-bound client, groups by origin (the map has one "you are here"), and attaches overlap, market facts, skill gap and OEWS history from two `"use cache"` functions keyed by origin and by origin/destination pair (public client, so nothing user-specific is cached). Pair overlap comes from `adjacent_occupations(origin, 1000)` because `adjacentRoutes` only returns a filtered top N. That RPC fails with the service-role client (`permission denied for view occupation_skill_centered`: the view is granted to `anon` and `authenticated` only), so call it with the anon or user client. `RouteVisualizer` (client) holds origin, selection, focus and view state: the navy console (map plus stat tiles), a light card with Demand over time (`TrendChart`), Side by side (`ComparisonBars`) and Skills (`SkillMatrix`), and `StatusTrack` for every saved route. Chart helpers shared with the landing page are in `lib/market/series.ts` (pure, client-safe). Motion: `components/ds/motion.css` holds opt-in one-shot entrance animations (`RouteMap entrance`, `TrendChart animate`); they only set a `from` state and are skipped for reduced motion. Each waits for `.md-in-view`, added by `components/ds/InView.tsx` the first time the section scrolls into view (the hold is scoped to `@media (scripting: enabled)`), so a chart below the fold plays when you reach it. Series are drawn as `<path>`, not `<polyline>`, because Firefox ignores `pathLength` on a polyline. The looping dot and pulse have a Pause animations button. Elements are keyed so selection changes never replay entrances (the map remounts only when the origin changes, each view remounts when opened). `RouteMap` puts one route on the middle line and two routes on the outer lines.

More than three routes: the design system has three route identities, so at most three routes are drawn on a map or chart at a time and the person chooses which; every other route is a plain row with no map line, chart colour or `RouteIndex`. On the landing page `LandingOrigin` (`lib/landing/types.ts`, client-safe; built by `lib/landing/bundles.ts`) carries every route on offer (the default charted three first, then up to five more, each with its raw OEWS `series` and `hasHistory`), `defaultCharted` and the origin's own `originSeries`. The chart arrays are not precomputed: `LandingExplorer` holds the charted SOC codes in state and calls `chartData(origin, charted)` (`lib/landing/chart-data.ts`, pure, uses `lib/market/series.ts`) so the ticks, shared year window and reference line follow the choice. `canChart()` refuses a route with under four annual estimates or too few years in common with the charted set, and the row says why. A listed route gets "Add ... to chart" while there is room, otherwise "Chart ... instead of {selected route}"; a charted route has "Remove from chart" while more than one is charted; focus moves to the selected route afterwards. The origin chip resets to `defaultCharted`, and the ticker uses only the default routes. In chat, `AdjacentCard` has a "Show more routes" button that calls the `moreAdjacentRoutes(originSoc, areaCode)` server action (`lib/chat/more-routes.ts`; reference data only, open to guests, no model call, up to 8 routes). A listed route's "Show on map" button adds it to the map, or swaps it for the highlighted route when the map is full; `selectedSoc` (facts line, any route) is kept apart from `slot` (the highlighted map line). `withLocalFigures()` in `lib/market/area-queries.ts` is the shared step that attaches local figures to an adjacent-roles result.

Chart axes (`components/ds/charts.tsx`, `axes.css`): `TrendChart` and `OpeningsChart` take optional `yAxis` (`{ title, ticks }`, ticks on the chart's 0-100 plot scale, drawn as gridlines) and `xLabels` (one per point or bar; every other interior label is hidden under 560px). With `xLabels` and `points` on the series, `TrendChart` also turns on a year readout: pointer, touch or Left/Right/Home/End/Escape on the focused plot picks a year, the legend values switch to that year, and a hidden table plus a live region carry the same values for screen readers. The line charts plot employment indexed to the first year (100 = that year) squeezed into a 12..88 band, so `indexAndScale()` in `lib/market/series.ts` also returns the matching `ticks` ("0%", "+20%", round values, always including the 0% baseline) and per-point `changes` ("+12%"); use those rather than inventing labels. `SHARE_OF_PEAK_TICKS` fits the charts whose values are already a share of the highest year (landing bars, the chat market card). Callers that pass none of these props render as before.

Landing page (`app/(site)/page.tsx`, `landing.css`, `components/landing/`): the design system's home-page order with real data. `lib/landing/bundles.ts` `getLandingOrigins()` (`"use cache"`, `cacheLife("days")`, cookie-free `createPublicClient()`) builds one bundle per curated origin chip (SOC codes in `ORIGINS`): the three routes with at least four years of OEWS history that are charted by default, further routes listed beyond them, skill stops, and the raw annual series the browser turns into chart values (see More than three routes). `LandingExplorer` (client) switches origins and routes instantly with no requests. Its hero "Create an account" button comes in as the `signUp` prop, a server-rendered `GuestSignUp` (Suspense + `connection()`) that renders nothing for signed-in users, so the client component never reads the session. Charts are real annual estimates, indexed to the first year, so they are not labelled "Illustrative"; there is no monthly openings or time-to-switch data, so neither is shown. The shared role queries (`adjacentRoutes`, `occupationSeries`, `skillGap`) live in `lib/market/queries.ts` and are also used by the chat tools. The page throws at build if the database is unreachable.
